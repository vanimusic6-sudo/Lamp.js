# Capsule Online — исследование жизненного цикла Skaz/Lampac
**Дата:** 19 ноября 2026  
**Версия исправлений:** 0.26.2  
**Основная проблема:** часть источников появлялась только после повторных входов в сериалы.

## Область подтверждения

Изучены:
- [Исходный сервер Lampac NextGen — `Online/OnlineApi.cs`](https://github.com/lampac-nextgen/lampac/blob/main/Online/OnlineApi.cs)
- [Оригинальный клиент Lampac NextGen — `Online/plugin.js`](https://github.com/lampac-nextgen/lampac/blob/main/Online/plugin.js)
- Исходник Capsule Online в `main`: `capsule-online.js`
- Локализованные поведенческие тесты: `tests/capsule-online-v025.test.cjs`

**Ограничение:** скачать и динамически исполнить конкретные скрипты `https://skaz.tv/amedia/a.js` и `https://skaz.tv/o.js` непосредственно из исследовательской среды не удалось. Lampac NextGen является открытым референсом механизма; совпадение деталей конкретного развертывания Skaz проверяется в Lampa на реальном устройстве. Следовательно, без фактических ответов Skaz нельзя утверждать, что каждый источник исправлен на сервере.

## Как реально работает серверный поиск Lampac

1. Клиент обращается к `/lite/events?life=true`. При включённом `checkOnlineSearch` сервер создаёт фоновые задачи проверки источников, кладёт их в память по `memkey` и возвращает в основном только `{ life: true, memkey }`. Это **не готовый каталог**.
2. `/lifeevents?memkey=…&seen=N` — инкрементальный long-poll. Сервер ждёт до 1,5 секунды новых результатов, после чего отправляет **полный накопленный снимок** с полями `online`, `ready`, `tasks`, `pending`, `head`.
3. `online` содержит завершённые проверки, в том числе `show:false` с URL провайдера; `pending` содержит ещё исполняющиеся задачи. `ready:true` означает, что все задачи закончили работу. Наличие четырёх URL **не** гарантирует `ready:true` и не является сигналом завершения.
4. `seen` равен числу уже завершённых элементов, включая `show:false`. Без него следующая итерация может хуже использовать механизм long-poll.
5. Серверный `checkSearch` получает идентификаторы TMDB/IMDb/KinoPoisk и может ждать HTTP-проверку провайдера до **10 секунд**. Ответы кэшируются на сервере: положительные примерно **10 минут**, отрицательные примерно **1 минуту**.
6. Без `life` или при отключённой автоматической проверке возможен **непосредственный массив** провайдеров (не объект `{online:…}`).
7. Оригинальный клиент Lampac сперва выполняет `externalids`, затем `createSource`. Для открытия самого балансера его `BALANCER_TIMEOUT` — **60 секунд**. Это не значит, что все запросы Capsule нужно растягивать на 60 секунд, но 3–4 секунды для холодного старта недостаточно.

## Подтверждённые регрессии Capsule до 0.26.2

| Место | Было | Почему ломалось |
| --- | --- | --- |
| `discoverProviderUpdates` | До 5 запросов или 8,5 секунды | Завершал поиск при `ready:false`, если backend всё ещё работал |
| `createSource` | Пытался использовать `online` из ответа `life:true` | В таком ответе могут быть только `life` и `memkey` |
| `createSource` / `withCatalog` | Ожидание завершалось после появления четырёх URL | `show:false` и ещё работающие задачи не учитывались |
| `this.initialize` | `externalids()` запускался без ожидания | `lite/events` уходил без IMDb/KinoPoisk ID; сервер кэшировал отрицательные проверки |
| `this.externalids` | Жёсткий лимит 1 секунда | ID приходили слишком поздно |
| `compareSeriesSources` | Лимит 3,3 секунды на меню | Холодные провайдеры могли вернуть пустой ответ/тайм-аут |
| `this.request` | Повторно скачивал уже проверенный корневой HTML | Источник становился «недоступным» между успешным сравнением и открытием |
| Кэш HTML | Мог удерживать HTML ошибки холодного источника | Повторный запрос получал закэшированную ошибку вместо новой проверки |

## Исправленная последовательность

```text
Card → externalids (с ограничением ожидания)
       → lite/events?life=true
       → memkey
       → lifeevents?memkey=…&seen=0
       → lifeevents?memkey=…&seen=число_завершённых
       → … до ready:true или конечного дедлайна
       → сравнение четырёх выбранных источников
       → однократный повтор холодного пустого корневого ответа
       → выбор по реальному охвату сезонов, языку, озвучке и качеству
       → повторное использование уже успешно загруженного корневого меню
       → плеер
```

Технические ограничения новой схемы:
- Серверный каталог ждём до **23 секунд**; число запросов не ограничивает преждевременно.
- Современный формат ждёт `ready:true`. Исключение — старый формат **без поля `ready`**, где допускается конец после проверки всех четырёх ссылок.
- Если `memkey` явно потерян, выполняется **один** резервный синхронный `lite/events?life=false`, вместо бессмысленного повторения устаревшего ключа.
- Нет сохранения промежуточных `lifeevents` в кэше. Корневое меню сохраняется кратковременно только при наличии распознаваемых `data-json` элементов.
- Подписанные меню видео и вложенные ссылки не сохраняются в длительный кэш.
- Для списка сериалов — Alloha, HDRezka, VIBIX, Filmix. Для фильмов — Alloha, HDRezka, Мир кино Z, Filmix.
- Для отладки в настройках «Система» добавлена кнопка **«Проверка каталога Skaz»**: она показывает состояние `ready`, `pending`, `tasks`, `seen` и семейства источников **без URL/токенов**.

## Дополнительный механизм: RCH

В серверном `OnlineApi.checkSearch` RCH-ответ с `"rch":true` считается признаком рабочего источника, даже когда обычного `data-json` HTML ещё нет. В оригинальном Lampac клиент при таком ответе запускает `rchRun` и повторяет запрос меню после регистрации сетевого моста.

**Новая регрессия, обнаруженная при аудите:** предварительный поиск Capsule воспринимал RCH JSON как пустую страницу и переходил к следующему источнику. После успешного RCH-подключения при ручном открытии другого тайтла тот же источник мог внезапно начинать работать.

Исправление: распознавание RCH как в объектном, так и в текстовом ответе; единый `ensureRchBridge` для одновременных запросов без конкурирующих повторных подключений; повтор исходного URL только после успешного подключения. Встроен отдельный ограничитель ожидания, чтобы отказ сетевого моста не зависал бесконечно. RCH-сообщения и WebSocket-ссылки **не сохраняются в кэше**.

## Проверка

Сценарии `node --test tests/capsule-online-v025.test.cjs` воспроизводят:
- долгий поиск до 9-го ответа и корректное продолжение при `ready:false`;
- накопительные `online` и параметр `seen`;
- `ready:true`, даже когда часть четырёх источников отсутствует;
- устаревший `memkey` и отсутствие вымышленных URL;
- непосредственный массив провайдеров;
- порядок `externalids` до `createSource`;
- повторную попытку для холодного пустого меню;
- повторное использование корневого HTML без нового запроса;
- распознавание RCH JSON, совместное подключение RCH и повтор после успешной регистрации моста;
- ограничение четырьмя выбранными провайдерами.

**Чего тесты не подтверждают:** фактические ответы конкретного экземпляра Skaz, состояние провайдеров на телевизоре, географические блокировки, авторизацию, успешность реального видеопотока. Итоговое подтверждение требует проверки в Lampa на устройстве с диагностикой.
